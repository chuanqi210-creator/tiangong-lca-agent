# TianGong-native LCA Agent 能力基础设施

本阶段把 TianGong 能力从“散落的命令、Skill 和接口”收敛成了一个
受版本、权限与审计约束的基础设施层。它没有启动研究案例、触发 LCIA
计算或评估组织形式优劣。

## 已经建立的能力底座

Agent 每次启动都必须先通过 D-18 启动清单。清单把产品身份、根本目的、
TianGong 权威边界、Project Record 唯一事实源、权限边界和非目标与精确
文件哈希绑定。架构、目录、来源锁或权限策略发生漂移时，启动会直接拒绝，
模型和工具不会被打开。

能力目录当前包含 53 项官方能力表面，覆盖规范、数据、原生工具、官方
Skills、MCP 工具、构建、验证、计算和证据处理。盘点粒度是官方接口与协议，
不是逐条枚举 Flow、Process 或结果数据。每项能力都有明确处置：

- 9 项已经统一接入；
- 9 项需要条件运行环境；
- 15 项需要人类责任动作；
- 20 项继续由 TianGong 上游拥有。

所有 53 项都已分类，没有未处置项。登记并不等于当前环境可以执行；条件
计算能力只证明合同和边界已经接好，不代表运行过计算。

## 来源、权限与执行

采用目录只接受精确版本、Git object、包完整性或静态工件哈希。CLI、
MCP server、TIDAS SDK、tidas-tools 与官方 Skills 都有来源锁；历史 CLI
和历史验收仍按原身份回放，不被新目录升级。发现新版本只会生成候选差异，
不会静默替换当前采用版本。

统一执行链是：

`目录查找 → Assurance 授权 → 适配器执行 → 结果归一化 → Assurance 记录 → Project Record`

Skill、MCP、模型和原生工具都不能直接写正式事实。适配器成功返回的仍是
“有来源的结果、尚非正式事实”，只有经过 LCA 规则校验和 Assurance 接受，
才能进入 Project Record。

权限、凭证、来源漂移、schema 漂移和无效结果都会关闭失败；只有明确标注
可重试的短暂传输错误或超时可以有界重试。运行收据保留来源锁、输入输出
哈希、适配器、耗时、尝试次数、效果类型、工件引用、失败分类和恢复路线，
但不保存秘密或未经裁剪的敏感输出。

## Agent 与旧 Skills 的处置

正式 Controller 已压缩为稳定 D-18 合同，不再内嵌历史案例、实验路线或
动态项目状态。`run-lca-research-project` 只负责启动检查和进入唯一产品
接口，不再向调用者暴露底层命令、工作流或手工路由。

旧 `evidence-to-tidas-lca` 以提交
`16609ccb1943b7da960de75dd4667f04cb699d1b` 中的不可变对象登记为
`legacy_adapter_only`。现场用户修改没有被覆盖。低层命令继续作为诊断、
恢复或历史回放端口，不再是默认用户入口。

## 当前能说与不能说的

可以确认：D-18 启动绑定已机械执行；已观察到的官方能力表面均已接入或明确
处置；可执行能力已有统一 Gateway、Assurance 和 Project Record 路径；
正式 Agent/Skill 已脱离案例专用默认路线。

不能声称：当前环境能执行目录中的所有能力；Agent 已支持全部 LCA 工作流；
条件计算就等于完成计算；任何能力组合或组织方式已经证明更优。

机器可验的完整处置账本位于
`docs/lca-agent-capability-infrastructure.json`。
